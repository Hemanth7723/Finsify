# Local build, run, and deployment troubleshooting

This guide covers the Flutter app in this repository (`lib/`). It is intended for local Android and iOS development and release preparation. The older Kotlin implementation under `Source/` has a separate build process.

## 1. Check the environment first

From the repository root:

```text
flutter --version
flutter doctor -v
flutter pub get
flutter analyze
flutter test
```

The current package constraint requires Dart `^3.13.2` (`pubspec.yaml`). Use a Flutter SDK that supplies a compatible Dart SDK; check `flutter --version` rather than guessing a version. Android uses the Gradle wrapper, Android Gradle Plugin, and Kotlin plugin declared under `android/`, with Java 17 source/target settings. Do not independently upgrade Gradle, AGP, Kotlin, or Flutter plugins to “latest” without checking compatibility as a set.

### Android prerequisites

- Android Studio or Android command-line tools, with an SDK platform and build tools compatible with the Flutter SDK/plugins.
- Android device or emulator; check detection using `flutter devices`.
- A compatible JDK. The app's Android compile options and Kotlin target are Java 17.
- Android SDK license acceptance (`flutter doctor --android-licenses`) when prompted.

### iOS prerequisites

- A Mac running macOS, Xcode, Xcode command-line tools, and an iOS simulator or registered physical device. iOS compilation, signing, and App Store deployment cannot be completed on Windows.
- A valid Apple Developer team and signing identity for device/release distribution.
- Resolve Flutter packages first (`flutter pub get`). This checkout contains Xcode workspace/project files and Flutter's generated iOS support files; it does not contain a checked-in `ios/Podfile`. Follow the dependency integration generated by the selected Flutter SDK rather than creating a Podfile or running `pod install` blindly.

## 2. Standard local workflow

### Android

```text
flutter devices
flutter run -d <android-device-id>
flutter test
flutter build apk --debug
```

For a release-mode local smoke test:

```text
flutter run --release -d <android-device-id>
```

For a distributable Android app bundle (after configuring release signing; see section 7):

```text
flutter build appbundle --release
```

Debug APK output is normally `build/app/outputs/flutter-apk/app-debug.apk`. Release artifacts are under `build/app/outputs/`.

### iOS (run these on macOS)

```text
flutter devices
flutter run -d <ios-simulator-or-device-id>
flutter test
flutter build ios --debug
```

For a signed distribution build, configure the Runner target's bundle identifier, team, and signing in Xcode, then use:

```text
flutter build ipa --release
```

Use `open ios/Runner.xcworkspace` on macOS to inspect signing, capabilities, and build settings in Xcode. If Flutter's generated project uses Swift Package Manager, let Flutter/Xcode resolve those dependencies.

## 3. Frequent build and run failures

### `Failed to find target with hash string 'android-37'`

**What it means:** A dependency's Android Gradle plugin requested Android SDK platform 37, but Gradle did not resolve a matching platform in the SDK location it is using. The SDK manager may appear to install a platform, while Gradle still reports it missing due to a version/platform mismatch or stale build configuration.

**Repository-specific fix:** This project uses `permission_handler: ^12.0.3` (Android implementation 13.0.1 through the resolved package graph), which avoids the earlier API 37 requirement from the newer plugin version. Keep `pubspec.lock` committed and do not upgrade `permission_handler` casually. If this error returns:

1. Check `flutter pub deps` for the resolved `permission_handler` and Android implementation versions.
2. Confirm the Android SDK path in `android/local.properties` points at the SDK you are actually maintaining.
3. Install the required SDK platform using Android Studio SDK Manager or `sdkmanager`, then accept licenses.
4. Run `flutter clean`, `flutter pub get`, and retry `flutter build apk --debug`.

Do not change `compileSdk` or SDK platform numbers randomly. This project sets `compileSdk = flutter.compileSdkVersion`; first identify which dependency requested the unavailable platform.

### Android Gradle/JDK errors

If Gradle reports an unsupported Java version, class-file version, Kotlin target, or plugin incompatibility:

1. Run `flutter doctor -v` and verify which Java executable Flutter uses.
2. Use a JDK version supported by the Flutter/Android Gradle Plugin combination in this repository. The app compiles Java/Kotlin for JVM 17.
3. Use the checked-in `gradlew` wrapper, not a separately installed arbitrary Gradle version.
4. Avoid changing one of Gradle, AGP, Kotlin, or JDK in isolation.

The Gradle wrapper URL and Android/Kotlin plugin versions are defined in `android/gradle/wrapper/gradle-wrapper.properties` and `android/settings.gradle.kts`.

### Dependency resolution or stale generated files

Try these in order:

```text
flutter pub get
flutter clean
flutter pub get
flutter build apk --debug
```

On macOS, repeat with `flutter build ios --debug`. Avoid deleting SDKs, user-wide Gradle caches, or lockfiles as a first-line fix. If the failure names one package, inspect its resolved version and plugin requirements before changing dependencies.

### iOS signing / provisioning errors

These are Xcode configuration issues, not Dart compilation errors. Open `ios/Runner.xcworkspace` on a Mac, select the Runner target, configure a unique Bundle Identifier, select the correct Team, and enable automatic signing or install the matching provisioning profile/certificate. A simulator build does not prove that a physical-device or App Store build is signed correctly.

### App installs but exits or shows a blank screen

- Capture the first Flutter exception and native stack trace; later log messages may be secondary.
- Try a full restart after native/plugin/manifest changes. Hot reload does not rebuild native Android/iOS code.
- Run `flutter analyze` and `flutter test`, then reproduce with a debug build.
- For plugin changes, run `flutter clean`, resolve packages again, and rebuild.

## 4. Known messages from previous local runs

### `OnBackInvokedCallback is not enabled`

The app manifest already enables `android:enableOnBackInvokedCallback="true"`. If an older installed build still prints the warning, rebuild and reinstall the current app. This was a warning, not a build failure.

### Gradle warning about `java.lang.System::load` native access

The warning mentioning Gradle's `NativeLibraryLoader` and `--enable-native-access=ALL-UNNAMED` is emitted by the Java/Gradle toolchain. It did not prevent the debug APK from building. Do not add JVM flags blindly; update the supported JDK/Gradle combination when the project toolchain is deliberately upgraded.

### Java 8 source/target compatibility warning from a plugin

This can be emitted by an Android dependency even though the app compiles for Java 17. If the build completes, it is informational. If it becomes an error after upgrading the Android toolchain, inspect the specific plugin's compatibility requirements before changing app-wide compiler settings.

### `Gralloc4`, `GraphicBufferAllocator`, or `AHardwareBuffer` errors for a tiny buffer

These messages often originate from the device GPU driver/emulator graphics stack. If the app still renders and there is no corresponding Flutter exception or visible rendering defect, they are not by themselves evidence of a Dart application failure. Reproduce on another emulator/device, update the emulator/system image or device firmware, and investigate only if there is an actual crash or visual corruption.

### `Duplicate GlobalKey`, `_InactiveElements.remove`, or framework assertion during hot reload

These indicate a widget-tree/lifecycle problem; they are not ordinary performance warnings. The app's dashboard add-form bridge now uses a `ValueNotifier` instead of a `GlobalKey`, and the profile theme preview avoids replacing a nested `Theme` during an open dialog. If similar errors recur:

1. Do a full hot restart/relaunch to rule out stale hot-reload state.
2. Capture the first assertion and widget stack trace.
3. Search for a `GlobalKey` attached to multiple mounted widgets, or a widget being reparented/disposed while still active.
4. Add a widget regression test for the exact interaction.

Do not suppress framework assertions or add duplicate keys to make the symptom disappear.

### `LateInitializationError` for `_screenTransitionController`

This previously came from a manually initialized animation controller during hot reload. Screen changes now use declarative `AnimatedSwitcher` transitions instead. If it returns, perform a full restart and inspect custom `AnimationController` initialization/disposal; do not assume every `LateInitializationError` has the same cause.

### Flutter `RenderFlex overflow`

The analytics bar chart was updated for tight height/width constraints. If an overflow returns on a specific device, capture the full render tree and viewport size; test with the same small-screen/text-scale constraints. Avoid fixing it by hiding the overflow with `ClipRect` unless clipping is the intended design.

## 5. Platform features and runtime permissions

| Feature | Platform/permission | Local validation |
|---|---|---|
| Voice expense entry | Device speech recognition and microphone permission; speech service availability varies | Grant microphone/speech access, test transcription, denial, and unavailable-recognizer states |
| SMS expense import | Android only; requests SMS permission only after user chooses import | Test granted, denied, permanently denied, empty inbox, and reviewed candidate import |
| Bill reminders | Android/iOS local notifications; permission requested when scheduling | Test permission, schedule, cancellation on paid/deleted, and reboot behavior on a physical device |
| XLSX Downloads export | Android only; Android 10/API 29+ `MediaStore.Downloads` | Export a non-empty filtered list and verify file in Downloads; confirm empty export reports a message |
| Investment/loan/bill records | Android/iOS Flutter preferences plugin; local device storage | Add records, restart app, and verify records reload |
| Expense ledger/profile/theme selection | Session memory in current implementation | Restarting the process clears expenses/profile/theme choice |

SMS import is not available on iOS. Direct XLSX saving is implemented through an Android method channel and is not available on iOS. Do not interpret successful iOS compilation as proof these Android-only flows are available there.

## 6. Validate before reporting a build as successful

From the repository root:

```text
flutter analyze
flutter test
flutter build apk --debug
```

On macOS, also validate the requested iOS target:

```text
flutter build ios --debug
```

For a release check, build the actual distribution artifact (`appbundle` for Google Play, `ipa` for App Store/TestFlight) using the intended signing configuration. A successful debug build does not validate release signing, store metadata, privacy disclosures, or platform feature behavior.

When triaging failure output, start at the **first** `FAILURE`, `Error`, or Dart exception. Lines marked `WARNING` may be non-fatal; verify whether Gradle/Xcode actually exited unsuccessfully before treating a warning as a blocker.

## 7. Release/deployment checklist

### Android / Google Play

- Replace the debug signing configuration in `android/app/build.gradle.kts` with a private release keystore configuration before publishing. **The current release build type uses the debug key and is not production-ready.**
- Keep keystore passwords and signing files out of source control. Load them from a secure local/CI secret store.
- Set a production application ID instead of the current template ID `com.example.finsify` before the first store release; application IDs cannot be changed for app updates.
- Increment `version` in `pubspec.yaml` (or pass `--build-name` and `--build-number`) for each release.
- Build and verify a signed app bundle: `flutter build appbundle --release`.
- Test on target Android versions, including runtime permission denial and notification scheduling behavior.
- Complete store declarations for SMS/permissions and user-data handling; requesting `READ_SMS` can trigger Google Play policy review. Keep SMS access limited to the explicitly user-initiated import feature.

### iOS / App Store or TestFlight

- Build from macOS with Xcode and configure the production bundle identifier, signing team, certificates, and provisioning.
- Confirm microphone and speech-recognition descriptions in `ios/Runner/Info.plist` accurately explain voice entry.
- Increase app version/build number and produce a signed archive/IPA.
- Test voice recognition, notification permissions/reminders, data persistence, and permission denial on real iOS hardware.
- SMS inbox import and direct Android Downloads export are not implemented for iOS.
